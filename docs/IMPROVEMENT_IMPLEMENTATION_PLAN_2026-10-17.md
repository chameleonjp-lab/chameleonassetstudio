# 改善要件と実装計画表

**議論用の草案です。追加実装や公開、MCP接続の承認を意味しません。**

このPRは文書のみをmain基準で提出します。以下のC0は別のローカル実装候補 `29ef7c6` であり、そのコード・派生台帳・実行ログは本PRに含めません。C0はリモート未提出のため、SHAだけで第三者が取得・再現できるとは保証しません。検証数はC0の観測であり、この計画PRのheadやmainの検証結果ではありません。

まず直すべき問題は、機能がないことよりも「何が使え、どこまで検証され、どの版に反映されているか」が一致していないことです。既存機能を作り直すのではなく、案内と台帳を正し、同じ候補版で受入を終える順序を提案します。MCPは、この受入を妨げない別レーンとします。

**元の独立性要件は、A00の単独の合格条件にします。** 新規cloneから、通常のNode.js・package manager・browser用標準ツールでinstall/run/test/buildできることを要求します。特定AI製品のCLI/SDK、ホスト済み実行環境、専用の秘密情報・URLを必須にしません。既存のclean worktreeでの成功だけで、この独立性を合格にしません。

### A00の判定を三つに分ける

1. **製品・build依存**: 製品コード、package scripts、build設定、fixtureに専用CLI/SDK・秘密情報・実行URLが必須になっていないかを監査する。特定環境の変数やファイルがないと動かない隠れた依存も対象とする。
2. **手順の再現性**: 通常のOSと標準Node/package managerだけを用意した空の作業環境で新規cloneし、READMEだけからinstall/run/test/buildとpreviewを実行する。既存node_modules、独自のhome配下設定、専用ホスト、専用資格情報に依存しない。browser試験に必要な標準browser/OS依存の導入はREADMEに書く。ソース取得の通常の読取権限や公開registryへの通信は、製品の専用サービス依存とは分けて扱う。
3. **CIの任意利用**: CIや開発支援として特定環境を便利に使うこと自体を不合格にしない。ただし、その外でも同じpackage scriptsと通常の手順で製品を実行・検査・buildできることが条件である。CI内だけの成功も、専用環境を使ったという理由だけの失敗判定も、独立性の根拠にしない。

証跡には、clone元と固定SHA、初期環境、OS/Node/package manager版、全実行コマンド、終了コード、生成物hash、必要な外部依存一覧を残す。環境変数は必要な名前・用途・必須/任意だけを記録し、秘密値をログへ出さない。A00はこの再現と監査が終わるまで未検証とする。

## 議論したい方針と推奨案

**1. 「全実装完了」ではなく、三つの状態を別々に確定する。**

実装済みでも、対象環境で未検証なら検証済みにはしません。候補ブランチにあっても、main・公開版の状態を更新しません。公開はmain反映と実配信確認も分けます。

**2. 最終受入を新機能追加より先にする。**

P0は実行基盤からの独立性、正本・機能案内の一致、同一SHA検査です。その後、現行機能を実機・支援技術・保存復旧・成果物まで通して確認します。ここで見つかった不具合は、関連実装・回帰テスト・証拠・台帳を一つの作業単位にして修正します。

**3. 自動削除は「期限切れだから安全」と決めない。**

crash残pin/stagingは当面保持し、今回の対象に自動削除を含めません。将来自動整理を必要とするなら、所有権、参照、回復可能性、同時実行、旧版との関係を先に設計し、救出可能な原本を失わない条件を別途合意します。

**4. MCPは接続方式から別計画で決める。**

特定AI製品に依存しない操作契約を先に定義し、読み取り専用の小試作で確認します。書き込み・削除・出力は、revision競合、差分確認、Undo、許可されたファイル境界を決めてからです。今回の必須実装には混ぜません。

MCP adapterより先に、特定のAI製品・クラウド・ホスト済み実行環境に依存しないcore操作契約を固定します。coreの入出力・revision・Undo・検査を通常のテストから実行でき、MCP未導入・無接続でも現行appのinstall/run/test/buildが成立することをA00で確認します。接続adapterは任意で差し替え可能とし、coreから専用SDKや秘密情報へ依存させません。導入が決まっても、現行の保存形式変更やクラウド同期を暗黙に含めません。

## まとまりある実装単位

1. **独立再現・案内・正本・台帳整合**: A00/A01とA04の表示改善。READMEの第三者手順、依存監査、実装、回帰、説明、状態更新を一組にする。
2. **同版検証・保存安全性**: A02/A03/A08。失敗した場合は原因に関係する修正をまとめ、テスト一件ごとのPRにしない。
3. **実機・アクセシビリティ・性能受入**: A05〜A07。端末と利用シナリオでまとめ、見つかった不具合と再検証を同じ単位で扱う。
4. **統合・公開判断**: A09。既存OPEN PRの目的と重複するなら更新を優先し、同じ目的のPRを増やさない。CI完了待ちやpollingを進行条件にしない。
5. **MCPは別の承認済work package**: M01→M02→M03/M04。現行機能の受入から切り離す。
