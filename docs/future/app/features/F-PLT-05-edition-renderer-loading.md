## 0. 完成系での位置づけ（逆算リンク）

由来する完成系（`features/README.md` 2 章）:

- **S-DONE-2**: 最小構成で軽く起動し、**使わない機能の重さを負わない**。
- **S-DONE-3**: 2D と 3D が、**別最適化されながら同じ操作感**で行き来できる。
- **S-DONE-1**: Home / Project Dashboard から 2D・3D いずれのプロジェクトへも入れる。

逆算の理由: ここは **`P5`（2D/3D の目的分離）と `P4`（未使用ゼロコスト）が交わる要所**である。Vision と Arch は「**2D 利用者は 3D の重い描画依存を 1 バイトも起動しない**（逆も同様）」と繰り返し宣言してきた（Arch 2 章、`APP_PRODUCT_VISION.md` 4.3）。だがその**実行層の要件が未定義**だった。

重要なのは、これが**単なる最適化ではない**という点である。描画ライブラリは本コンセプトで最も重い依存になりうる（Comp 2-D の候補群）。ここで分離を徹底できなければ、**「軽量が前提」という中心命題が最初に破れる場所**になる（`APP-RISK-03`「重い依存が Core/Shell へ染み出す」）。

関係マップのノード: `PF4 描画ライブラリ edition別`（本機能が実現）、`A3 Edition Runtime`（載せる先）、`P5 目的分離`、`P4 ゼロコスト`。

## 1. ユーザーストーリー

- 2D だけを使う制作者として、**3D の重さを一切負いたくない**。
- 3D だけを使う制作者として、同様に **2D の描画依存を背負いたくない**。
- 制作者として、2D と 3D を**同じアプリから自然に行き来**したい（別アプリに感じたくない）。
- 制作者として、描画が使えない環境でも**理由が分かり、作業内容が失われない**でほしい。

## 2. 用語

- **Edition Runtime**: 2D / 3D それぞれの実行基盤（Arch 2 章の `A3`）。
- **レンダラ**: 描画ライブラリと、それを載せる薄い適合層。
- **エディション切り替え**: 別エディションのプロジェクトを開く操作（同一プロセス内 / 別ウィンドウ / 別プロセスのいずれかは実装判断）。

## 3. 機能要件（FR）

### 3.1 一方だけを載せる

- **FR-1** **起動時にどちらのレンダラも載せない**。プロジェクトのエディションが決まった時点で、**必要な一方だけ**をロードする（`P4` / F-CORE-09 FR-5 の遅延ロードと同じ原則）。
- **FR-2** **2D 利用者の環境に 3D 描画依存を載せない**（逆も同様）。両方を同時に常駐させない。
- **FR-3** レンダラ依存は **Edition Runtime の内側に閉じる**。**Core / Shell へ染み出させない**（`APP-RISK-03`、F-PLT-01 FR-8）。

### 3.2 切り替えと共存

- **FR-4** **エディションの切り替え**ができる（別エディションのプロジェクトを開ける。`S-DONE-1`）。
- **FR-5** 切り替え時、**使わなくなったレンダラの資源を解放**できる（載せっぱなしにしない。`P4`）。
- **FR-6** 切り替えは**作業を壊さない**。未保存の変更は F-CORE-01 FR-10 の保存確認に従う。
- **FR-7** 2D と 3D で**操作感・見た目の一貫性**を保つ（`S-DONE-3`）。レンダラが違っても、UI の作法を変えない。

### 3.3 失敗と環境差

- **FR-8** 描画の初期化に失敗した場合（ドライバ非対応・GPU 利用不可等）、**理由を文章で示す**（`S-DONE-4`）。無言で真っ黒な画面にしない。
- **FR-9** 描画が使えなくても、**プロジェクトデータを失わない**。保存・書き出しの経路を可能な限り残す（描画不能 ≠ データ喪失）。
- **FR-10** 環境差（GPU の有無・ドライバ差）を**吸収するか、できない場合は明示**する。黙って品質を落とさない。

### 3.4 選定基準（採用ではなく、判断の条件）

- **FR-11** レンダラ候補は **F-PLT-04 の同一手順**で比較する。比較する観点は最低限:
  - Edition Runtime のロード時間と常駐（**分離の効果が実測で確認できるか**）
  - 代表描画の性能（2D: 大きな canvas・多数レイヤー／3D: 代表モデルの表示・検品）
  - 対象環境での動作（GPU 差・ドライバ差）
- **FR-12** 採用前に **ライセンス・商用利用**を `G1` と同じ厳格さで確認する（未確認なら採用しない）。
- **FR-13** 判断材料と結論を **ADR に記録**する（`APP-O-03` の解消）。

## 4. 非機能要件（NFR）

- **NFR-1（ゼロコスト分離）**: 使わないエディションの描画依存が、**起動・常駐・インストーラに乗らない**（`P4`。F-PLT-04 で実測）。
- **NFR-2（境界の堅さ）**: レンダラ依存が Core / Shell に漏れない（FR-3）。
- **NFR-3（一貫性）**: エディションが違っても操作感が揃う（FR-7）。
- **NFR-4（非破壊）**: 切り替え・描画失敗でデータを失わない（FR-6/FR-9）。
- **NFR-5（応答性）**: レンダラのロードが UI を固めない（`PF3`）。

## 5. データ・保存への影響

- **レンダラの選択・ロード状態はアプリ実行時の情報**であり、**プロジェクト保存の器（F-CORE-05）に含めない**。
- **プロジェクトのエディション（2D / 3D）は保存データの属性**（F-CORE-01 FR-1/FR-3）。本機能はそれを読んで**どちらを載せるかを決める**だけで、エディションを書き換えない。
- 描画不能でも、**保存・書き出しの経路を可能な限り維持**する（FR-9）。

## 6. 依存機能

- **F-CORE-01**（ライフサイクル）: プロジェクトのエディション判定（FR-1）。
- **F-PLT-01**（外殻）: Edition Runtime を一方だけ載せる方針の実行主体（F-PLT-01 FR-4）。
- **F-PLT-03**（offload）: ロードの非同期化（NFR-5）。
- **F-PLT-04**（計測）: 分離効果の実測と候補比較（FR-11 / NFR-1）。
- **F-CORE-09**（Host）: 遅延ロードの原則を共有。
- **F-2D-03 / F-3D-03**（各ビューポート）: 実際の描画利用者。

## 7. 受け入れ条件（Acceptance）

- **AC-1**: **起動直後はどちらのレンダラも載っていない**（FR-1、F-PLT-04 の 3 状態測定で確認）。
- **AC-2**: 2D プロジェクトを開いた環境で、**3D 描画依存が常駐していない**（逆も同様）（FR-2/NFR-1）。
- **AC-3**: レンダラ依存が **Core / Shell から参照されていない**（FR-3/NFR-2）。
- **AC-4**: エディションを切り替えても**作業が壊れず**、未保存変更は保存確認に従う（FR-4/FR-6）。
- **AC-5**: 切り替え後、**使わなくなったレンダラの資源が解放**される（FR-5、実測で確認）。
- **AC-6**: 描画初期化に失敗しても、**理由が示され、データを失わない**（FR-8/FR-9）。
- **AC-7**: 2D と 3D で **UI の作法が揃っている**（FR-7）。
- **AC-8**: 候補比較が F-PLT-04 の同一手順で行われ、**ライセンス確認と ADR 記録**を経ている（FR-11/FR-12/FR-13）。

## 8. 非目標

- **描画ライブラリの採用決定**（`APP-O-03`。実測 + ライセンス + 人間承認 + ADR の後）。
- 各エディションの**描画内容・機能**（F-2D-03 / F-3D-03 と各エディション仕様）。
- 外殻方式の決定（F-PLT-01 / `APP-R-01`）。
- 2D と 3D の**同一画面統合**（Vision 10 章の禁止事項。編集画面は分ける）。
- WebGPU 等の必須化（現行方針と同じく、必須要件にしない）。

## 10. Open questions

- エディション切り替えの実現方式（同一プロセス内 / 別ウィンドウ / 別プロセス）。外殻方式（`PF5`）と連動。
