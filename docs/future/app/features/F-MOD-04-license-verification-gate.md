## 0. 完成系での位置づけ（逆算リンク）

由来する完成系（`features/README.md` 2 章）:

- **S-DONE-2**: 最小構成で軽く起動し、**必要な機能だけをインストール**して広げられる。

逆算の理由: 「必要な機能を後から足せる」製品は、**足せる候補が法的に配布・利用できる**ことが前提になる。F-MOD-01 は未検証を「表示のみ・導線抑止」とし、F-MOD-02 は「verified のみ導入可」とし、F-MOD-03 は「依存込みで verified を確認」とした——**3 つとも同じ前提に寄りかかっているが、その判定の正本がまだ無い**。本機能がその **enforcement の正本**である。

あわせて、`APP-D-05`（決定: 未確認は導入導線を出さない）と `APP-RISK-05`（勢いでの未確認採用）を塞ぐ機構でもある。

関係マップのノード: `G1 ライセンス検証 gate`（本機能が実現）、`A6 Manifest 契約`（license メタの出所）、`F-MOD-02`（導入可否の最終判定）、`F-MOD-03`（依存込み集約）、`F-CORE-07`（帰属表示の書き出し先）。

## 1. ユーザーストーリー

- 制作者として、**入れた機能が原因で、後から配布できなくなる**ことは絶対に避けたい。
- 制作者として、**商用利用してよいのか**を、入れる前にはっきり知りたい。
- 制作者として、**自分が作ったアセットの権利**が、使ったモジュールに侵食されないと確認したい。
- 制作者として、**帰属表示（クレジット）が必要なら、その義務をどこで果たすか**を示してほしい。

## 2. 用語

- **license メタ**: モジュールが宣言するライセンス情報（識別子、商用利用可否、再配布条件、帰属表示の要否）。
- **verified**: **人間が確認し、その記録が残っている**状態。単なる自動判定ではない。
- **評価記録**: 誰が・いつ・どの version の何を確認したかの記録（系譜: 現行 `CLAUDE.md` の「採用する PR で評価記録を新規作成」）。
- **失効（revocation）**: 後からライセンス条件の問題・変更が判明し、verified を取り消すこと。

## 3. 機能要件（FR）

### 3.1 宣言と検証

- **FR-1** 各モジュールは **license メタ**を宣言する（`A6`）: ライセンス識別、**商用利用可否**、再配布条件、**帰属表示の要否**。
- **FR-2** **`verified` は人間の確認と評価記録に裏づけられる**。自動判定だけで verified にしない（系譜: 現行の採用規律）。
- **FR-3** **評価記録は辿れる**（誰が・いつ・**どの version** を・何を根拠に確認したか）。
- **FR-4** 評価記録は **version に紐づく**。モジュールの version が上がったら、**再確認が必要**な状態として扱う（前 version の verified を自動で引き継がない）。

### 3.2 ゲート（enforcement の正本）

- **FR-5** **`verified` でないモジュールは導入できない**。未宣言・不明・期限切れも同様に**保守的に「不可」**とする（F-MOD-02 FR-9 / F-MOD-01 FR-7 の判定元）。
- **FR-6** **依存込みで判定する**。推移的依存に 1 つでも未検証があれば、**全体として導入不可**（F-MOD-03 FR-9 の enforcement）。「本体は verified だが依存が未検証」を通さない。
- **FR-7** 拒否は**理由を示す**（どのモジュール／依存の、何が未確認か）。黙って選択肢を消さない。
- **FR-8** ゲートを**迂回する経路を作らない**（「一時的に無視して入れる」を既定で提供しない）。

### 3.3 義務と境界

- **FR-9** **帰属表示が必要なモジュール**については、その義務を果たせる場所を提供する（アプリ内クレジット等）。必要なら**書き出し成果物にも同梱**できるようにする（`F-CORE-07` の器に載せる）。
- **FR-10** **ツールのライセンスと、制作物の権利を区別して示す**。モジュールのライセンスは、**利用者が作ったアセットの権利を侵食しない**——ただし、モジュールが**素材や生成物を同梱・出力に混ぜる**種類のものである場合は、その影響を**明示する**（両者を混同させない）。
- **FR-11** **失効を扱える**。後から問題が判明した場合、**新規導入を止め、利用者へ通知**する。すでに導入済みの環境と**進行中の作業・プロジェクトデータは壊さない**（無断で機能を消さない）。

## 4. 非機能要件（NFR）

- **NFR-1（保守的既定）**: 不明・未宣言・判定不能は、すべて **「導入不可」側**に倒す。
- **NFR-2（監査可能性）**: なぜ導入できた／できなかったかを、記録から後追いできる（FR-3）。
- **NFR-3（オフライン）**: 判定はローカルの宣言と記録で完結し、ネットワーク到達性に依存しない。
- **NFR-4（透明性）**: 利用者に**判断材料と理由**を出す。ゲートをブラックボックスにしない。
- **NFR-5（非破壊）**: 失効の反映が、進行中の作業やプロジェクトデータを壊さない（FR-11）。

## 5. データ・保存への影響

- **license メタ・評価記録・verified 状態は、アプリ / カタログ側**の情報。**プロジェクト保存の器（F-CORE-05）には含めない**（F-MOD-01/02/03 と同じ分離）。
- 例外的な接点は **帰属表示**: 書き出し成果物に attribution を同梱する場合、**export の器（F-CORE-07）に載せる**（README / import notes と同じ扱い）。これは成果物側の要件であり、プロジェクトの編集データではない。

## 6. 依存機能

- **A6 / Manifest 契約**: license メタの出所（FR-1）。
- **F-MOD-01**（カタログ）: 未検証の表示と導線抑止（本機能が判定元）。
- **F-MOD-02**（導入/撤去）: 導入可否の最終判定を本機能に仰ぐ（FR-5）。
- **F-MOD-03**（依存解決）: 依存込み集約の結果を検証する（FR-6）。
- **F-CORE-07**（書き出しフレーム）: 帰属表示の同梱先（FR-9）。
- **F-MOD-05**（プロファイル）: 一括導入も同じゲートを通る。

## 7. 受け入れ条件（Acceptance）

- **AC-1**: `verified` でない／未宣言のモジュールは、**理由つきで導入できない**（FR-5/FR-7）。
- **AC-2**: 本体が verified でも、**依存に未検証があれば全体として導入不可**になる（FR-6）。
- **AC-3**: 評価記録から、**誰が・いつ・どの version を確認したか**を辿れる（FR-3）。
- **AC-4**: モジュールの version が上がると、**再確認が必要な状態**として扱われる（FR-4）。
- **AC-5**: 商用利用可否が、**導入前に判断材料として示される**（FR-1）。
- **AC-6**: 帰属表示が必要な場合、義務を果たす場所があり、必要なら**書き出しに同梱**できる（FR-9）。
- **AC-7**: ライセンスが失効しても、**導入済み環境と作業・プロジェクトデータが壊れない**まま、新規導入が止まり通知される（FR-11/NFR-5）。
- **AC-8**: ゲートを既定で迂回する手段が存在しない（FR-8）。

## 8. 非目標

- **法的助言そのもの**。本機能は「確認したことを記録し、未確認を通さない」仕組みであり、法解釈を代替しない。
- ライセンスの**全自動判定だけで承認**すること（FR-2 に反する）。
- 第三者モジュール market の審査運用（Stage 4、`G4`）。
- 課金・価格・販売（本コンセプトの非目標）。
- 具体的なライセンス識別子の網羅表（実装時の資料）。
