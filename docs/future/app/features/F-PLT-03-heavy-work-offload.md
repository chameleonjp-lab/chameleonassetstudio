## 0. 完成系での位置づけ（逆算リンク）

由来する完成系（`features/README.md` 2 章）:

- **S-DONE-2**: 軽く動く（`P1` の「重すぎるなら使われない」は**起動の軽さだけでなく、操作中の手応え**でもある）。
- **D-DONE-2 / T-DONE-6**: 大きな画像の編集、3D の軽量化——**本質的に重い処理**を扱う。
- **S-DONE-4**: 失敗・制限が文章で分かり、手動で必ず回復できる。

逆算の理由: **すでに 8 つの仕様が「UI を固めない」を非機能要件に掲げている**（F-CORE-01 / 03 / 04 / 05 / 09、F-MOD-02 / 03、F-PLT-01）。しかし**その実現手段の正本が無い**——最も多くの機能から依存されている未定義機能だった。

同時にここは、**ネイティブ化の最大の見返り**でもある（Arch 6 章: 真の並列・SIMD・GPU compute・メモリ制約からの解放）。ブラウザ制約を外す意味が、最も具体的に現れる場所である。

関係マップのノード: `PF3 重い処理 offload`（本機能が実現）、`PF1 性能予算`（応答性）、`A4 Feature Modules`（モジュールの重い処理も同じ仕組みへ）、`G5 非破壊`（中断しても壊さない）。

## 1. ユーザーストーリー

- 制作者として、重い処理の最中でも**画面が固まらず、他の作業や取り消しができる**でほしい。
- 制作者として、**どれくらい待つのか**が分かると安心できる。
- 制作者として、**間違えて始めた重い処理を止められる**と嬉しい。止めても壊れないでほしい。
- 制作者として、処理が失敗したら**理由が分かり、手でやり直せる**でほしい。
- 制作者として、**端末が熱くなって重くなる**ような使い方をされたくない。

## 2. 用語

- **重い処理**: UI の 1 フレーム内に収まらない処理（大画像処理、atlas packing、mesh 簡略化、テクスチャ圧縮、保存・読み込み、migration、書き出し等）。
- **offload**: 重い処理を UI から切り離して実行すること（別スレッド / 別プロセス / ネイティブ側 / GPU）。
- **高速経路**: SIMD・GPU compute 等の、使える環境でのみ速くなる実行経路。
- **fallback**: 高速経路が使えない環境で用いる通常経路。

## 3. 機能要件（FR）

### 3.1 UI を止めない

- **FR-1** **重い処理を UI から外して実行**する。対象は「1 フレームに収まらないもの」全般（2 章の例）。
- **FR-2** 実行中も **UI は応答する**（入力・スクロール・パネル操作・キャンセルが効く）。
- **FR-3** **進捗を示す**。長い処理は、進んでいることと（可能なら）残りの目安を示す。

### 3.2 中断と一貫性

- **FR-4** 重い処理を **キャンセルできる**。
- **FR-5** **完了・失敗・キャンセルのいずれでも、Document は一貫状態**を保つ。**中途半端な派生を残さない**（`G5` / F-CORE-03）。
- **FR-6** 重い処理は **1 つの履歴単位**として扱う（F-CORE-04 のトランザクション）。キャンセルした処理は履歴に**残さない**。
- **FR-7** 失敗時は**理由を文章で示し、手動で回復できる**（`S-DONE-4`）。無言で失敗しない。

### 3.3 資源の使い方

- **FR-8** **並列度を制御**する。端末を飽和させず、他の作業や OS を圧迫しない。
- **FR-9** **高速経路（SIMD / GPU 等）は任意**とし、**使えない環境では fallback で成立**させる。高速経路を必須要件にしない（`capabilities` の `gpu-optional` の考え方。Arch 3 章）。
- **FR-10** 大きなデータの受け渡しで **無駄な複製をしない**（F-CORE-03 NFR-4「巨大 Source を無用に複製しない」の実現側）。
- **FR-11** 省電力状態・発熱・バッテリー動作を**考慮する**（F-PLT-04 FR-9 が記録する条件と対）。

### 3.4 モジュールとの関係

- **FR-12** **モジュールの重い処理も同じ仕組みに乗せる**。モジュールが独自にスレッドを乱立させることを許さない（`A9` / F-CORE-09 が経路を保証、`A8` が権限を制限）。
- **FR-13** モジュールの重い処理も、**キャンセル・進捗・失敗表示の同じ扱い**を受ける（体験の一貫性）。

## 4. 非機能要件（NFR）

- **NFR-1（応答性）**: 重い処理中でも UI の手応えが保たれる（`PF1` の応答性予算内）。
- **NFR-2（非破壊）**: 中断・失敗が Source と Document を壊さない（`G5`。例外なし）。
- **NFR-3（ゼロコスト整合）**: offload 基盤そのものが常駐を膨らませない（`P4` と矛盾しない）。
- **NFR-4（可観測性）**: 実行中・完了・失敗・キャンセルの状態が分かる。
- **NFR-5（環境非依存の成立）**: 高速経路が無くても機能が成立する（FR-9）。
- **NFR-6（節度）**: 端末の資源・電力・熱を不必要に消費しない（FR-8 / FR-11）。

## 5. データ・保存への影響

- **中断された処理の中間物を保存に混ぜない**。派生（Derivation）は**完了時にのみ確定**する（F-CORE-03）。
- 実行状態（進捗・キュー）は**揮発**であり、プロジェクト保存の器（F-CORE-05）に含めない。
- 保存・migration 自体が重い処理になりうるため、**原子的保存（F-CORE-01 FR-8）と両立**させる（中断時に既存の保存済みを壊さない）。

## 6. 依存機能

- **F-PLT-01**（外殻）: プロセス / スレッド構成の土台（F-PLT-01 FR-3 の受け皿）。
- **F-CORE-03**（非破壊）: 派生の確定単位（FR-5）。
- **F-CORE-04**（履歴）: 重い処理のトランザクション化（FR-6）。
- **F-CORE-09**（Host）: モジュール処理の受け入れ経路（FR-12）。
- **F-CORE-10**（権限）: GPU・サブプロセス等の capability 制御（FR-9 / FR-12）。
- **F-PLT-04**（計測）: 応答性の実測（NFR-1）。

## 7. 受け入れ条件（Acceptance）

- **AC-1**: 代表的な重い処理の実行中に、**UI が応答し続ける**（入力・キャンセルが効く）（FR-1/FR-2）。
- **AC-2**: 長い処理で**進捗が示される**（FR-3）。
- **AC-3**: 実行中の処理を**キャンセルでき**、キャンセル後に **Document が一貫**し、**中途半端な派生が残らない**（FR-4/FR-5）。
- **AC-4**: キャンセルした処理が**履歴に残らない**／完了した処理は **1 回の Undo で戻る**（FR-6）。
- **AC-5**: 失敗時に**理由が文章で示され**、手動で回復できる（FR-7）。
- **AC-6**: **高速経路が使えない環境でも**、同じ機能が（遅くとも）成立する（FR-9/NFR-5）。
- **AC-7**: **モジュールの重い処理**も、同じキャンセル・進捗・失敗表示の扱いを受ける（FR-12/FR-13）。
- **AC-8**: 保存・migration の中断で、**既存の保存済みデータが壊れない**（5 章 / F-CORE-01 AC-2）。

## 8. 非目標

- 並列化の実装方式（スレッドプール / worker / IPC / GPU API）の**決定**（外殻方式 `PF5` の確定後）。
- 個々の重い処理のアルゴリズム（atlas packing、mesh 簡略化等は各機能／モジュール）。
- 応答性の**数値目標**（F-PLT-04 の実測 + 人間承認）。
- 分散実行・クラウドオフロード（本コンセプトの非目標）。
