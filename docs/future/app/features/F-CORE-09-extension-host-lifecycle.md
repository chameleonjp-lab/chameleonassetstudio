## 0. 完成系での位置づけ（逆算リンク）

由来する完成系（`features/README.md` 2 章）:

- **S-DONE-2**: 最小構成で軽く起動し、**必要な機能だけをインストール**して広げられる。使わない機能の重さを負わない。
- **S-DONE-5**: **どのモジュール構成でも同じプロジェクトを開け**、未知データを壊さない。
- **S-DONE-4**: 失敗・制限が文章で分かり、手動で必ず回復できる。

逆算の理由: モジュールは、入れたら**アプリの一部として振る舞う**必要がある。つまり「**誰が登録し、いつ載せ、いつ降ろし、何を許すか**」を握る受け皿が Core 側に要る。すでに **F-CORE-04**（モジュール操作の履歴登録）、**F-MOD-02**（有効化/無効化）、**F-MOD-04**（導入ゲート）、**F-MOD-01**（導入状態）が、この受け皿の存在を前提にしている。本機能はその **`A9 Extension Host` の正本**である。

関係マップのノード: `A9 Extension Host`（本機能が実現）、`A2 Core 契約`（Host は Core の一部）、`A4 Feature Modules`（管理対象）、`D3`/`D4`（構成非依存・名前空間の enforcement 側）。

## 1. ユーザーストーリー

- 制作者として、入れた機能が**アプリに馴染んで**動いてほしい（別世界の異物にならない）。
- 制作者として、外した機能の**ボタンやパネルが残骸として残らない**でほしい。
- 制作者として、**ある機能が壊れてもアプリ全体が道連れにならない**でほしい。壊れた場所と理由が分かれば対処できる。
- 制作者として、**入れていない機能があっても、プロジェクトは開ける**と信じたい。

## 2. 用語

- **拡張点（Extension point）**: Core が公開する「機能を足してよい口」（パネル、ツール、検品ルール、export preset など）。
- **提供物（provides）**: モジュールが拡張点へ登録するもの（`A6` manifest の宣言に対応）。
- **ライフサイクル状態**: 未導入 / 導入済み（未ロード）/ 有効（ロード済み）/ 無効 / 失効。
- **縮退（degrade）**: あるモジュールが失敗したとき、その機能だけを落として全体を続行すること。

## 3. 機能要件（FR）

### 3.1 登録と拡張点

- **FR-1** Host は**導入済みモジュールを把握**し、その**提供物を Core の拡張点へ登録**する。
- **FR-2** モジュールは **Core が公開した拡張点だけ**を通して機能を足す。**Core の内部実装へ直接触らせない**（境界を曖昧にしない）。
- **FR-3** **どのモジュールが何を登録したか**を観測できる（残骸・出所不明の UI を生まない）。

### 3.2 ライフサイクル

- **FR-4** Host は**ライフサイクル状態**を持ち、遷移を明示的に扱う（未導入 / 導入済み・未ロード / 有効 / 無効 / 失効）。
- **FR-5** **遅延ロード**: 導入済みでも**起動時にはロードしない**。初回利用時に載せる（`P4`、F-MOD-02 FR-2 の受け皿）。
- **FR-6** **有効化・無効化を安全に行う**。実行中の作業を壊さず載せ／降ろす。降ろすときは**登録した提供物を確実に撤去**する（コマンド・パネル・preset を残さない。F-MOD-02 の「残渣ゼロ」の UI 側）。
- **FR-7** **`coreContract` 範囲外のモジュールをロードしない**（`A6`。導入時の判定は F-MOD-03、実行時の最終防波堤は Host）。
- **FR-8** **失効**（F-MOD-04 FR-11）を受けて、新規ロードを止めつつ**進行中の作業を壊さない**。

### 3.3 隔離と縮退

- **FR-9** **失敗隔離**: モジュールの失敗が**アプリ全体を落とさない**。失敗したモジュールを特定し、**その機能だけ縮退**して続行する。
- **FR-10** 失敗と縮退の**理由を文章で示す**（`S-DONE-4`）。無言で機能が消えない。

### 3.4 Core 契約の受け皿

- **FR-11** モジュールの**編集操作を Core の履歴経路へ登録**する（F-CORE-04 FR-8 の受け皿。独自の隠れ履歴を許さない）。
- **FR-12** モジュールのデータ書き込みを、**自分の名前空間の内側に強制**する（`D4`。越境を拒否）。
- **FR-13** **未導入・無効のモジュールがあってもプロジェクトは開ける**。提供物が無いだけで、**データは保持**される（`D3`、F-CORE-05 の往復）。

## 4. 非機能要件（NFR）

- **NFR-1（ゼロコスト）**: 未ロードのモジュールは**常駐しない**。Host 自体も痩せている（`P4`）。
- **NFR-2（隔離）**: 1 つの失敗が全体へ波及しない（FR-9）。
- **NFR-3（決定性）**: 登録順・解決順が再現し、構成が同じなら同じ状態になる。
- **NFR-4（応答性）**: ロード・登録・撤去が UI を固めない（F-PLT-03）。
- **NFR-5（可観測性）**: 現在の状態（何が有効で、何を登録し、何が失敗したか）を確認できる。

## 5. データ・保存への影響

- **ライフサイクル状態・登録内容はアプリ環境レベル**。**プロジェクト保存の器（F-CORE-05）に含めない**（F-MOD 群と同じ分離）。
- Host は **`D4` 名前空間の enforcement 点**であり、モジュールのデータ書き込み境界を実行時に守らせる。
- **未導入でもデータは保持**（`D3`）。Host は「解釈できる提供物が無い」ことを示すだけで、データを消さない。

## 6. 依存機能

- **F-CORE-05**（保存/名前空間）: 書き込み境界の定義元（Host が強制側）。
- **F-CORE-04**（履歴）: 履歴経路の定義元（Host が登録側）。
- **F-CORE-10**（capability 権限）: 権限の強制は Host が実行する（`A8` 強制 `A9`）。
- **F-MOD-02**（導入/撤去）: 有効化/無効化の要求元。
- **F-MOD-03 / F-MOD-04**: `coreContract` 判定・失効の情報源。
- **F-PLT-03**（offload）: ロード・撤去の非同期化。

## 7. 受け入れ条件（Acceptance）

- **AC-1**: 導入済みモジュールの提供物が拡張点へ登録され、**どこから来たか観測できる**（FR-1/FR-3）。
- **AC-2**: 導入済みでも**起動時にロードされず**、初回利用でロードされる（FR-5、`P4`）。
- **AC-3**: 無効化・撤去で、**登録された UI・コマンド・preset が残らない**（FR-6）。
- **AC-4**: 1 つのモジュールが失敗しても**アプリが落ちず**、その機能だけ縮退し、**理由が文章で示される**（FR-9/FR-10）。
- **AC-5**: モジュールの編集操作が**同じ Undo で戻せる**（FR-11、F-CORE-04 AC-5 と対）。
- **AC-6**: モジュールが**自分の名前空間の外へ書けない**（FR-12）。
- **AC-7**: 未導入・無効のモジュールのデータを含むプロジェクトが**開けてデータが保持**される（FR-13）。
- **AC-8**: `coreContract` 範囲外のモジュールが**ロードされない**（FR-7）。

## 8. 非目標

- capability（権限）の種類と強制ポリシーそのもの（**F-CORE-10**）。
- 拡張点の具体 API 形状（実装時に確定）。
- 第三者拡張のサンドボックス強度（Stage 4、`G4`）。
- モジュールの取得・配布（F-MOD-02）。
