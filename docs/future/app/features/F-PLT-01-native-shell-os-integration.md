## 0. 完成系での位置づけ（逆算リンク）

由来する完成系（`features/README.md` 2 章）:

- **S-DONE-2**: **最小構成で軽く起動**し、必要な機能だけを入れて広げられる。
- **S-DONE-3**: 2D と 3D が、別最適化されながら**同じ操作感**で行き来できる。
- **S-DONE-4**: 失敗・制限が文章で分かり、手動で必ず回復できる。

逆算の理由: 本コンセプトの出発点は「**ブラウザ制約を前提にしない**」ことだった（`APP_PRODUCT_VISION.md` 2 章）。だがそこには落とし穴がある——**制約を外すために重い外殻を選べば、「軽量が前提」という中心命題そのものを失う**（Arch 6 章）。外殻は「何を得るか」だけでなく「**何を失わないか**」で選ばねばならない。本機能は、その**要件と選定基準**を定める `A1` / `PF5` の正本である。

**採用判断は含まない。** 物差し（F-PLT-04）で測ったうえで、人間が決める。

関係マップのノード: `A1 Shell 外殻`（本機能が実現）、`PF5 外殻方式`（選定基準）、`P4 未使用ゼロコスト`（Shell は痩せたまま）、`PF1`/`PF2`（予算と実測）。

## 1. ユーザーストーリー

- 制作者として、**すぐ起動して、すぐ描き始めたい**。待たされたくない。
- 制作者として、**OS のファイルダイアログや D&D が普通に使える**と嬉しい（ブラウザの制限に付き合いたくない）。
- 制作者として、**大きな素材を扱ってもアプリが固まらない**でほしい。
- 制作者として、**ネットに繋がっていなくても全部できる**と信じたい。

## 2. 用語

- **外殻（Shell）**: ウィンドウ・OS 連携・プロセス構成を担う最も外側の層（Arch 2 章の Shell）。
- **常駐部**: 起動している限りメモリに載り続ける部分。
- **システム WebView 型**: OS 提供の WebView を使う方式（ランタイムを同梱しない）。
- **ランタイム同梱型**: ブラウザエンジン等を同梱する方式。

## 3. 機能要件（FR）

### 3.1 外殻が担うこと

- **FR-1** ウィンドウ管理（生成・複数ウィンドウ・状態復元）を担う。
- **FR-2** **OS 連携**を担う: ネイティブなファイルダイアログ、ドラッグ&ドロップ、最近使った項目、関連付け（プロジェクトファイルを開く）、クリップボード。
- **FR-3** **プロセス / スレッド構成**を持ち、重い処理を UI から逃がせる土台を提供する（F-PLT-03 の受け皿）。
- **FR-4** **Edition Runtime を一方だけ載せる**（2D か 3D）。他方の重い描画依存を持ち込まない（`P5` / Arch 2 章）。
- **FR-5** **オフラインで完全に動作**する。ネットワーク到達性を起動・編集・保存・書き出しの前提にしない。
- **FR-6** OS 権限（ファイルアクセス等）を **F-CORE-10 の capability へ対応付ける**土台を提供する。

### 3.2 外殻が担わないこと（境界）

- **FR-7** **Shell に機能を足さない**。Shell と Core は痩せたまま保ち、機能は Edition Runtime とモジュールへ置く（`P4` / Arch 2 章）。
- **FR-8** 重い依存（描画・画像処理・3D）を **Shell に染み出させない**（`APP-RISK-03`）。

### 3.3 選定基準（採用ではなく、判断のための条件）

- **FR-9** 外殻方式の候補は、**F-PLT-04 の同一手順**で比較する（`E91`）。比較する指標は最低限:
  - 冷間起動時間 / 常駐メモリ（最小構成）/ 最小インストーラサイズ
  - 代表操作の応答（大画像・多数レイヤー）
  - 対象 OS すべてでの動作（**片方だけ速い**方式を採らない）
- **FR-10** 次を**採用前に確認**する（`APP-R-01` の「実測後に確定」を具体化）:
  - **性能**: 上記指標が `PF1` の予算方針を満たしうるか
  - **描画適性**: 2D canvas / 3D 描画（`PF4`）を必要な品質で載せられるか
  - **OS 差**: WebView 等の実装差が、対応 OS 間で許容できる範囲か
  - **ライセンス・商用利用**: `G1` / F-MOD-04 と同じ厳格さで確認（未確認なら採用しない）
  - **体制**: 採用言語・技術を保守できるか（`APP_ROADMAP_DECISIONS_OPEN_ITEMS.md` 4 章の open item）
  - **セキュリティ境界**: `F-CORE-10` の最小権限を実装できるか（`APP-RISK-07`）
- **FR-11** **単一指標で決めない**。「インストーラが小さい」だけ、「実績がある」だけで選ばない（FR-10 の全項目を並べて人間が判断する）。
- **FR-12** 判断材料と結論を **ADR として記録**する（`APP-R-01` / `APP-O-03` の解消）。

## 4. 非機能要件（NFR）

- **NFR-1（軽量が前提）**: 外殻の選択が「軽量である」という中心命題を損なわない。**外殻を理由に重くなることを許容しない**。
- **NFR-2（ゼロコスト維持）**: Shell の常駐が最小構成の予算内に収まる（`P4` / `PF1`）。
- **NFR-3（応答性）**: 重い処理中も UI が固まらない（FR-3 / F-PLT-03）。
- **NFR-4（オフライン）**: FR-5 を全機能で満たす。
- **NFR-5（一貫性）**: 対応 OS 間で操作感が大きく変わらない（`S-DONE-3` の土台）。
- **NFR-6（安全）**: ネイティブ化を理由に安全境界を緩めない（`APP-RISK-07`）。

## 5. データ・保存への影響

- 外殻はファイル I/O の**実行主体**であり、**原子的保存（F-CORE-01 FR-8 / F-CORE-05 FR-12）を実現できる手段**を提供しなければならない（詳細は F-PLT-02）。
- ウィンドウ位置・サイズ等は **セッション状態**であり、**プロジェクト保存の器に含めない**（F-CORE-01 6 章の分離）。
- 外殻方式の選択が**保存形式を規定しない**（`APP-O-01` は独立して決める）。

## 6. 依存機能

- **F-PLT-04**（計測）: 候補比較の物差し（**先行必須**。`E91`）。
- **F-PLT-02**（ファイル I/O）: 原子的保存・ダイアログの実体。
- **F-PLT-03**（offload）: スレッド／プロセス活用の実体。
- **F-PLT-05**（レンダラのロード）: Edition 別描画の載せ方。
- **F-CORE-10**（権限）: OS 権限との対応付け（FR-6）。
- **F-CORE-09**（Host）: 失敗隔離の強度は外殻構成に依存（F-CORE-09 Open question と対）。

## 7. 受け入れ条件（Acceptance）

- **AC-1**: 外殻候補が **F-PLT-04 の同一手順**で比較され、結果が記録されている（FR-9）。
- **AC-2**: FR-10 の**全項目**（性能・描画適性・OS 差・ライセンス・体制・セキュリティ）が確認され、**未確認項目が残っていない**（残るなら採用しない）。
- **AC-3**: 対象 OS **すべて**で必要水準を満たすことが示される（片方だけ良い方式を採らない）（FR-9）。
- **AC-4**: 最小構成で **OS のファイルダイアログ・D&D・関連付け**が使える（FR-2）。
- **AC-5**: **ネットワーク遮断状態**で、作成・編集・保存・書き出しが完了できる（FR-5 / NFR-4）。
- **AC-6**: Shell の常駐が最小構成の予算内に収まる（NFR-2、F-PLT-04 の実測で確認）。
- **AC-7**: 重い処理中も UI が固まらない（NFR-3）。
- **AC-8**: 判断材料と結論が **ADR に記録**され、人間が承認している（FR-12 / `APP-R-01`）。

## 8. 非目標

- **外殻技術の採用決定**（実測 + ライセンス + 体制 + 人間承認の後。`APP-R-01`）。
- 描画ライブラリの採用決定（`APP-O-03` / F-PLT-05）。
- ファイル I/O の詳細方式（F-PLT-02）。
- 並列処理の詳細設計（F-PLT-03）。
- モバイル / タブレット対応方針（`F-UX-04`）。
- 配布・署名・更新の仕組み（別途。`APP-O-02` と関連）。
