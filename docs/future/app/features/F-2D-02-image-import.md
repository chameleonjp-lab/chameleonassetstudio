## 0. 完成系での位置づけ（逆算リンク）

由来する完成系（`features/README.md` 2 章）:

- **D-DONE-1**: 空キャンバス／テンプレート／**画像取り込み**／図形／パーツから新規作成できる。
- **D-DONE-2**: 取り込んだものを**非破壊で編集・修正**できる。

逆算の理由: **F-2D-01 が「起点の実体は F-2D-02」と明示的に委ねていた**未定義部分。そして**外部の信頼できないファイルがアプリに入ってくる唯一の入口**でもあり、**安全性・正直さ・非破壊が最も試される場所**である。

関係マップのノード: `F-2D-01`（起点の呼び出し元）、`F-PLT-02`（安全な読み込み）、`G5 非破壊`（原本保持）、`F-CORE-06`（loss の提示）。

## 1. ユーザーストーリー

- 制作者として、**手持ちの画像から作り始めたい**。
- 制作者として、**GIF などのコマ**をそのままアニメーションとして取り込みたい。
- 制作者として、**取り込めない形式**なら、**理由と代わりの手順**を教えてほしい。
- 制作者として、**取り込みで劣化する部分があるなら、事前に知りたい**（後で気づくのが最悪）。
- 制作者として、**元ファイルが書き換えられない**と確信したい。
- 制作者として、**複数ファイルの取り込みが途中で失敗したとき、half-done な結果が残らない**でほしい。

## 2. 用語

- **原本（source）**: 取り込んだ元のファイルの中身（バイト列）。
- **rasterized-import**: 画素として取り込む（ベクター構造は保持しない）。
- **frame 列として取り込む**: 複数コマを持つ形式を、フレームとして写す。
- **unsupported**: 対応しない（理由と代替手順を示す）。
- **loss（欠落）**: 取り込みで失われる情報。

## 3. 機能要件（FR）

### 3.1 形式の扱いと表示（継承）

- **FR-1** 対応形式を **「どう扱われるか」で分類・表示**する（系譜: ADR-0016）: **画像として取り込む / コマ列として取り込む / 対応していない（+ 理由）**。形式名だけを並べない。
- **FR-2** **未実装・この環境で扱えないものを「対応済み」と表現しない**（系譜: ADR-0016。F-CORE-07 の `verified` 規律と同じ思想）。
- **FR-3** **対応しない形式は、理由と代替手順を示す**（例: 別形式で書き出してから取り込む）（系譜: ADR-0016/0020）。
- **FR-4** **「原本だけ保存して編集できない」扱い（reference-only）を採らない**（系譜: ADR-0016）。
  **理由（継承）**: **容量を消費しながら編集できない状態**を作り、**対応していると誤解させる**ため。

### 3.2 安全な取り込み（継承）

- **FR-5** **信頼しないファイルを安全に扱う**（F-PLT-02 FR-7 の実行層）。**能動的な構造（スクリプト・外部参照・埋め込み実行要素など）を含むものは、取り込み前に理由つきで拒否**する（系譜: ADR-0020）。
- **FR-6** **原本を書き換えない・サニタイズしない**（系譜: ADR-0020）。**原本はそのまま（verbatim）保持**し、編集や表示用の画素だけを別に作る（`G5` / F-CORE-03 FR-3.1 / ADR-0019）。
- **FR-7** **codec を動かす前に、境界内で事前検査（bounded preflight）**する（系譜: ADR-0020）: 宣言された寸法・コマ数・範囲の妥当性。**上限を超えるものは、切り捨てずに理由つきで拒否**する。
- **FR-8** **拒否の種類を区別**する（系譜: ADR-0020）: **「壊れている」もの**と、**「壊れてはいないが受け入れない構造」**を同じ扱いにしない（後者を破損として隔離保存しない）。

### 3.3 原子性（継承）

- **FR-9** 複数ファイルの取り込みは、**全件の準備が成功した場合にだけ確定**する。**1 件でも失敗したら、プロジェクト・アセット・データを 1 件も保存しない**（系譜: ADR-0020）。**half-done を残さない**。
- **FR-10** 途中失敗・キャンセルで、**既存のプロジェクトを壊さない**（F-PLT-03 FR-5 / F-CORE-02 と整合）。

### 3.4 コマ列の取り込みと loss（継承 + 本コンセプト固有）

- **FR-11** **複数コマを持つ形式をフレームとして取り込める**。取り込み先は **`F-2D-07` のフレーム／アニメーション**とする。
- **FR-12** **対応環境では全コマを取り込む**。扱えない環境では**先頭コマのみ**とし、**その旨を loss として示す**（系譜: ADR-0020）。
- **FR-13** **途中まで成功した decode を「成功」として扱わない**（系譜: ADR-0020）。**部分成功を成功と報告しない**（F-CORE-07 NFR / F-2D-07 と同じ規律）。
- **FR-14** **時間情報の写像は決定的**である（同じ入力→同じ結果）（系譜: ADR-0020）。
  **本コンセプト固有の差**: 上流は保存形式の制約から**一律 fps へ写像**していたが、**本コンセプトは可変時間を持てる**（`F-2D-07` FR-5）。したがって **可能な範囲で元の時間を保持**し、**保持できない部分だけを loss として示す**。上流から継承するのは**「一律化する」制約ではなく、「決定的に写し、失うものを必ず示す」規律**である。
- **FR-15** **ループ回数などを保守的に写像**し、**表現できない場合は勝手に別の意味へ変えない**（例: 有限回のループを無限ループにしない）。**loss として示す**（系譜: ADR-0020）。

### 3.5 loss の開示（継承 — 重要）

- **FR-16** **変換で失われるものを、確定前に必ず説明する**（系譜: ADR-0020）: ベクター構造・形式固有の情報・時間・ループ・先頭コマのみへの縮退など。
- **FR-17** **loss や警告がある場合、利用者の明示的な確認を求める**（系譜: ADR-0020）。**黙って進めない**。
- **FR-18** 取り込み後も、**何が失われたかを後から確認できる**（provenance / report。F-CORE-06 の report と接続）。

### 3.6 修復（取り込み後の手当て）

- **FR-19** 取り込んだ画像に対する**基本的な修復**（切り抜き・余白調整・不要部分の除去など）を、**非破壊で**行える（実体の編集操作は `F-2D-05` に載る）。
- **FR-20** 修復は**原本を変更しない**。派生として持ち、**やり直せる**（F-CORE-03）。

## 4. 非機能要件（NFR）

- **NFR-1（安全性）**: 信頼しない入力でアプリが壊れない・意図しない実行が起きない（FR-5/FR-7）。
- **NFR-2（非破壊）**: 原本を書き換えず、verbatim 保持する（FR-6。`G5`。例外なし）。
- **NFR-3（原子性）**: 全件成功でのみ確定し、half-done を残さない（FR-9）。
- **NFR-4（正直さ）**: 対応度合いと loss を誇張せず、確定前に示す（FR-2/FR-16/FR-17）。
- **NFR-5（決定性）**: 同じ入力に対し同じ取り込み結果になる（FR-14）。
- **NFR-6（応答性）**: 大きな画像・多数コマでも UI を固めない（`PF3`）。

## 5. データ・保存への影響

- **原本は Source として verbatim 保持**（FR-6。F-CORE-03 / ADR-0019 の前例）。表示・編集用の画素は**派生**。
- 取り込み時の **loss 記録・出所（provenance）** を残せるようにする（FR-18）。**編集データとは分けて**扱う（F-CORE-05 の名前空間）。
- 取り込みが**保存形式に新しい情報を要求する場合**（例: 原本の種類）、F-CORE-05 の版・移行の判断を通す（ADR-0019 の前例と同じ経路）。

## 6. 依存機能

- **F-2D-01**（新規作成）: 呼び出し元（起点）。
- **F-PLT-02**（ファイル I/O）: 安全な読み込み・ダイアログ・D&D（FR-5）。
- **F-CORE-03**（非破壊）: 原本保持（FR-6/FR-20）。
- **F-CORE-05**（保存形式）: 原本と派生の持ち方。
- **F-CORE-06**（検品）: loss の提示・report（FR-18）。
- **F-2D-07**（フレーム）: コマ列の取り込み先（FR-11）。
- **F-2D-05**（ラスタ編集）: 修復操作の実体（FR-19）。
- **F-PLT-03**（offload）: 重い decode の逃がし先（NFR-6）。

## 7. 受け入れ条件（Acceptance）

- **AC-1**: 形式が **「どう扱われるか」で表示**され、**未対応は理由と代替手順つき**で示される（FR-1/FR-3）。
- **AC-2**: 扱えないものが **「対応済み」と表示されない**（FR-2）。
- **AC-3**: **原本だけ保存して編集できない状態を作らない**（FR-4）。
- **AC-4**: 能動的構造を含むファイルが、**取り込み前に理由つきで拒否**される（FR-5）。
- **AC-5**: **原本がバイト不変**で保持される（FR-6/NFR-2、F-CORE-03 AC-6 と対）。
- **AC-6**: 上限超過が **切り捨てられず、理由つきで拒否**される（FR-7）。
- **AC-7**: 複数取り込みで **1 件でも失敗したら、何も保存されない**（FR-9/NFR-3）。
- **AC-8**: **部分的な decode 失敗が「成功」として扱われない**（FR-13）。
- **AC-9**: **loss が確定前に示され、確認なしに進まない**（FR-16/FR-17）。
- **AC-10**: **可能な範囲で元の時間が保持**され、保持できない分だけが loss として示される（FR-14）。
- **AC-11**: 修復が**非破壊**で、原本が変わらない（FR-19/FR-20）。

## 8. 非目標

- **対応形式の最終確定**（どの形式をどう分類するかは、実装時に評価記録つきで決める。上流も分類変更は別 ADR を要求）。
- **外部 parser ライブラリの採用**（採用は `G1` / F-MOD-04 と同じ厳しさのライセンス評価を要する）。
- ベクター構造を保持したままの編集（将来の別判断）。
- 動画編集の代替（系譜と同じく目指さない）。
- ラスタ編集ツールそのもの（`F-2D-05`）。
